# Chrysalis engineering review — 2026-09-15

## Conclusion

Chrysalis has useful foundations for continuing development while its owner uses a separate personal vault: Markdown storage, synthetic tests, shared agent instructions, and an updater with previews and rollback. Its next investment should be a repeatable development and release process, followed by repairs to data preservation and planning accuracy.

Background development is feasible. The current checkout is not ready for unattended release: five existing tests fail, several important failure cases pass unnoticed, and there is no checked-in CI workflow or development scheduler. Startup context hooks do not provide that scheduler.

The desired outcome is less time administering Chrysalis and more time pursuing personal goals. Use [BACKGROUND-DEVELOPMENT.md](BACKGROUND-DEVELOPMENT.md) for the setup sequence and [BACKLOG.md](BACKLOG.md) for bounded engineering work.

## Findings

P1 means address before unattended use of the affected behavior. P2 means an important reliability or integration improvement. These are release priorities, not claims that every finding was introduced by the current dirty diff.

### R1 — P1: Calendar refresh can corrupt memory or erase valid commitments

**Evidence:** [fetch_ical.py](../System/scripts/fetch_ical.py), calendar YAML construction and `update_scheduling_memory` (approximately lines 361–445), and `sync_ical` (449 onward).

Calendar titles and locations are interpolated into quoted YAML without escaping. A synthetic title containing quotation marks, `Review "draft"`, produced invalid YAML. The memory file is then replaced directly without validating the complete result.

A second probe supplied an HTTP 200 HTML sign-in page. The importer reported success, replaced an existing cached commitment with an empty list, and recorded a new synchronization time. It does not distinguish a valid empty calendar from a response that is not a calendar.

**Impact:** A routine refresh can damage scheduling state or make occupied time appear free.

**Repair:** Validate calendar structure; use a YAML serializer; validate the whole memory document; replace atomically; retain the previous valid cache and report failure when input is invalid. Cover quotes, multiline text, empty valid feeds, HTML, interrupted writes, and preservation of unrelated state.

### R2 — P1: Calendar timezone and recurrence handling silently changes commitments

**Evidence:** [fetch_ical.py](../System/scripts/fetch_ical.py), `parse_ical_dt` and recurrence expansion (approximately lines 70–104 and 233–307).

| Synthetic input | Observed result | Required behavior |
| --- | --- | --- |
| New York event at 09:00 on September 15, displayed in Chicago | 09:00 with local offset | 08:00 with local offset |
| Monthly event beginning August 15, queried for September 15 | No event | September occurrence present |
| Monday recurrence every two weeks, September 7–21 | September 7, 14, 21 | September 7 and 21 |

The parser ignores `TZID`, uses a fixed offset, supports only a subset of recurrence frequencies, and does not honor `INTERVAL` in the tested weekly case. Exception instances also need a defined contract.

**Impact:** Imported commitments can be omitted, shifted, or multiplied without an error.

**Repair:** Adopt a supported calendar parser or explicitly reject unsupported features. Use named timezone rules for conversion while continuing to serialize explicit local offsets as required by Chrysalis. Test daylight-saving transitions, recurring overrides, exclusions, all-day events, and cross-midnight commitments.

### R3 — P1: Doctor success is too weak to authorize automation

**Evidence:** [doctor.py](../System/scripts/doctor.py), schema checks (81–112), timestamp validation (123–175), template fallbacks (178–188 and 314–324), and final verdict (450 onward).

A synthetic task missing creation timestamps, with `urgency_tier: 99`, `timeEstimate: -5`, and `scheduled: tomorrow`, received a successful result with no errors. Its scheduled value was counted as an explicit local timestamp. A completely empty temporary vault also returned success: source templates can stand in for missing live state.

**Impact:** A nightly job or deployment gate could accept unusable state. Existing tests do not establish the advertised complete schema check.

**Repair:** Separate installation readiness from template validation. Validate required live files, actual task types/ranges/enums, and parsed timezone-aware timestamps. Report missing prerequisites explicitly. Until then, use doctor as one diagnostic alongside specific acceptance checks.

### R4 — P1: Appending to a malformed mailbox destroys pending contents

**Evidence:** [substrate_mailbox_client.dart](../apps/mobile/lib/transport/substrate_mailbox_client.dart), `readEvents` and append logic (approximately lines 56–90).

Read/JSON errors become an empty event list. The next append writes that list plus the new event over the original file. A malformed synthetic queue containing an earlier intent was replaced with one new command and reported success.

The default destination is `chrysalis/System/Inbox/events.json`; legacy reads use `System/Inbox/events.json`. [hybrid_orchestrator_transport.dart](../apps/mobile/lib/transport/hybrid_orchestrator_transport.dart) still reports the old path, and two tests expect it. Correcting those expectations alone does not repair corruption handling.

**Impact:** Offline commands can disappear. The instance-level write lock also does not coordinate independent writers or cloud synchronization.

**Repair:** Preserve malformed bytes and surface a recoverable failure. Verify legacy migration and configured destinations. Introduce stable event IDs and acknowledged execution before adding a consumer. A queued event currently has no automatic execution or cross-device delivery guarantee.

### R5 — P1: The dirty task schema drops framework functionality

**Evidence:** [_types/task.md](../_types/task.md), compared with `git show HEAD:_types/task.md`; three framework test failures.

The working diff removes `version: 0.2.0`, `archived`, `startedAt`, and `completedAt`. It also removes `linked_zettels`, `project_ref`, and `x-chrysalis` metadata, which those three failures do not fully cover. Its generated-file notice creates an ownership conflict between plugin-generated settings and framework-maintained fields.

**Repair:** Reconcile the complete schema while preserving compatible TaskNotes annotations. Establish which source owns each field and prevent plugin regeneration from silently removing framework fields. Keep regression coverage for the whole maintained contract.

### R6 — P1: Mobile calibration presents a preview as a committed plan

**Evidence:** [home_screen.dart](../apps/mobile/lib/presentation/screens/home_screen.dart), schedule regeneration and calibration (approximately lines 108–152); [morning_calibration_sheet.dart](../apps/mobile/lib/presentation/widgets/morning_calibration_sheet.dart), button text; [bio_cognitive_scheduler.dart](../apps/mobile/lib/domain/services/bio_cognitive_scheduler.dart).

The calibration callback changes an in-memory schedule and sends `/morning`. That callback does not itself persist scheduled task timestamps, morning memory, or a daily note, or verify that the remote command persisted them. Subsequent cache updates regenerate using fallback inputs, losing the selected calibration. The button nevertheless says “Calibrate Today & Lock Sprints.”

The local scheduler does not consume imported commitments, approved roadmap priorities, or the complete runtime scheduling policy. A synthetic archived task was assigned a sprint because candidate filtering excludes only completed tasks.

**Repair:** Make preview, queued request, verified persisted plan, and failed execution visible states. Retain selected calibration inputs. Exclude archived tasks. Later, persist a versioned plan through one authoritative policy implementation and verify its receipts before reporting success.

### R7 — P1: Pause and learning instructions permit repeated or out-of-order mutation

**Evidence:** [evening runbook](../.agent/skills/evening/SKILL.md), audit before pause check; [audit runbook](../.agent/skills/audit/SKILL.md), learning in Step 1 and auto-pause evaluation in Step 5; [calibrate runbook](../.agent/skills/calibrate/SKILL.md); [Scheduling Memory template](../System/_templates/Scheduling-Memory.template.md).

Evening invokes the audit before its pause gate. Audit applies learning over recently completed tasks without an explicit initial freeze gate or processed-session record. Repeating that runbook can apply learning to the same session again. Nested morning/calibration instructions repeat related state transitions, and a response timestamp is treated as a wake timestamp even when someone answers late.

The template also contains competing pause/state locations and advertises a mobile calendar bridge as active despite unfinished application wiring.

**Evidence level:** Instruction and configuration review; no unattended agent was run against a personal schedule.

**Repair:** Define one state machine: check pause first, identify the approved plan revision, process each completed session once, and record actual wake input separately from response time. Reconcile templates through explicit schema versions. Runtime skill edits require the existing backup and interactive development procedure.

### R8 — P2: Task completion does not establish a usable duration

**Evidence:** [home_screen.dart](../apps/mobile/lib/presentation/screens/home_screen.dart), completion handler (approximately lines 170–186); [task_note.dart](../apps/mobile/lib/domain/models/task_note.dart), `transitionTo`.

The UI completes a task directly without first starting it. A synthetic `todo` to `done` transition recorded `completedAt` but no `startedAt`, leaving actual duration unknown. Completion feedback implies that telemetry was recorded. Obsidian timestamp workflow files also remain in source while their workflow-engine bundle is removed in the current diff; their presence alone does not establish execution.

**Repair:** Provide an explicit start/completion lifecycle, or clearly represent an unknown duration. Learning must skip incomplete telemetry and avoid counting the same session twice. Verify the actual plugin dependency in a release fixture.

### R9 — P1 before shared storage: Capture and synchronization can overwrite independent edits

**Evidence:** [vault_synchronizer.dart](../apps/mobile/lib/data/sync/vault_synchronizer.dart), generated paths (241–247), mutation drain, and remote deletion handling.

New filenames use the current date plus a title slug. Independent captures with the same title on the same day can target the same path. Synchronization writes do not compare the previous remote revision, cache and journal updates are separate operations, and remote deletion handling needs to preserve dirty local work.

**Evidence level:** Code-path review; concurrent device behavior was not reproduced in this session.

**Repair:** Give captures stable unique identities, make cache/journal changes transactional, and retain conflicting revisions. Test process interruption, repeated delivery, simultaneous edits, and deletion with pending local work before wiring the Google Drive provider into startup.

### R10 — P2: Gateway success does not prove a runtime action

**Evidence:** [orchestrator_bridge.py](../apps/gateway/orchestrator_bridge.py), process launch and response handling; [ambient_gateway_client.dart](../apps/mobile/lib/transport/ambient_gateway_client.dart).

The adapter invokes deployment-specific `new-conversation`/`send-message` commands, inherits its process directory, and has a 60-second timeout. Executable presence and process exit success do not prove that the correct vault was selected or changed. Mobile requests do not carry a retained conversation ID, so follow-up approval cannot depend on an established conversation alone.

**Repair:** Verify the installed CLI's actual contract, select the runtime explicitly, distinguish service health from backend readiness, and return durable execution receipts. Preserve the existing distinction between timeout and safely retryable failure. Use a separate development runner for engineering; the gateway currently serves runtime/mobile transport.

### R11 — P2: The privacy scanner is narrower than the audit contract

**Evidence:** [pii-scanner.sh](scripts/pii-scanner.sh), compared with [audit-dev Protocol 1](skills/audit-dev/SKILL.md).

The script scans tracked working files and selected patterns in the staged diff. It does not automatically include eligible untracked additions, and it does not implement all of the runbook's Windows-user-path and personal-email checks. A passing script result therefore does not establish the complete audit promised by the runbook.

For this review, a temporary source-only Git snapshot included all 330 existing eligible files before running the scanner. An additional Windows-path/email-pattern inspection found existing vendor attribution, asset-name matches, synthetic calendar fixtures, and a Git transport address. Some fixtures use non-reserved example domains and should be normalized. None of these observations is evidence that the private vault was exposed.

**Repair:** Make candidate contents the explicit scan input; reconcile the implemented checks and documented exceptions; normalize synthetic fixture addresses; retain human review of actual additions. B01 includes this work. Do not describe a pattern scan as proof that arbitrary private information cannot be present.

Watch software, additional AI backends, broad ingestion, and native calendar export should follow a dependable capture-to-vault-to-plan loop. They are larger commitments and would add maintenance before the current loop is reliable.

## Recommended engineering order

1. Restore a passing source baseline while preserving the existing dirty work.
2. Automate deterministic validation and candidate privacy checks.
3. Rehearse one isolated background implementation followed by a separate review of its exact result.
4. Repair calendar preservation, mailbox preservation, and doctor validation.
5. Make mobile preview and execution states accurate; then harden capture and synchronization.
6. Consolidate planning/learning behavior and complete one end-to-end user workflow.
7. Automate release preparation, previews, and rollback rehearsals; introduce bounded runtime promotion after the release process is proven.

This review produced documentation, a prioritized backlog, and reusable execution prompts. It did not repair application code, enable a persistent job, commit, push, deploy, or change personal runtime state.
