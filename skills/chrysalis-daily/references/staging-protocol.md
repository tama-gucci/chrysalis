# Staging and feedback
Ask for additions, changing constraints and priority intent. Read Life-Roadmap and active project
deliverables first. Active roadmap work anchors peak focus; additions fit their modality windows.
If no imminent roadmap deadline exists, a requested task may be the anchor. Query `gap-fillers`
for unblocked unscheduled quick-capture tasks first; label inferred backlog alternatives explicitly.
Do not materialize unrelated inferred work merely to fill a table.
Build a prototype with `stage` using the morning protocol's windows and actual calendar/transit
commitments. It proposes pending prototype state without changing task timestamps or wake learning.
Combine additional task captures and roadmap edits through `propose`, retaining original revisions.
Present the table, origins, constraints and digest. An approved application
persists pending staging state; the schedule's feedback branch is distinct from proposal approval.
Approval of the agenda leads to calibration; requested modifications produce a newly reviewed
proposal; no reply remains pending without an arbitrary timer. At the next cycle boundary, audit
proposes auto_unresponsive pause, preserving multipliers. Never serialize unreviewed scheduled blocks.
Institutional submissions are excluded on weekends; use `business-buffer` to reserve 3–5 business
days between submission and verification. Routing duration and buffer remain separate from task
work estimates. Persist only provider-permitted location/route fields.
